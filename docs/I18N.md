# Internationalization (i18n) — Architecture & Decisions

Status: **Foundation landed** (PUP-475). Epic: **PUP-473**.

This document records the architectural decisions behind Code Puppy's i18n
system and gives translators a quickstart. It is the living answer to the
"Open Questions" section of PUP-473.

---

## 1. Initial target locales

The first languages we translate to are:

| Locale   | Catalog file              | Notes                                    |
|----------|---------------------------|------------------------------------------|
| `en-US`  | `locales/en-US.json`      | Source / default. Never missing a key.   |
| `es`     | `locales/es.json`         | Spanish base — the Latin American `es-419` copy has been folded in here. |
| `fr-CA`  | `locales/fr-CA.json`      | Canadian French specifically.            |

> **Note on `es-419`:** the Latin American Spanish umbrella tier has been
> **deprecated**. Its strings were folded into the base `es.json`, so there is
> no `locales/es-419.json` anymore and the resolver no longer probes for one.
> Regional dialects override `es` directly (see below).

### Central & South American Spanish dialects

Every Central/South American country's Spanish falls back to the base `es`
catalog, then `en-US`:

```
es-AR -> es -> en-US     (Argentina, voseo)
es-MX -> es -> en-US     (Mexico)
es-CO -> es -> en-US     (Colombia)
...
es-ES -> es -> en-US     (Spain, same plain-truncation chain)
```

This is plain BCP-47 truncation in `fallback_chain` (`code_puppy/i18n/locale.py`).
To add a specific country dialect (e.g. Argentine voseo), create
`locales/es-AR.json` containing **only** the strings that differ from `es` —
everything else is inherited automatically.

`PARENT_LOCALES` (in the same module) remains available as a CLDR override
seam if a non-truncation parent is ever needed again (e.g. reintroducing an
`es-419` umbrella), but it currently ships empty.

#### Regional dialect files

Regional dialect catalogs are **not shipped until they contain reviewed
translations**. Until then, regional tags fall back through the base `es`
catalog automatically. When a dialect is ready, add `<locale>.json` with only
the keys that genuinely differ from `es` — do not copy the whole catalog.

Call `code_puppy.i18n.available_locales()` for the live list of shipped catalogs.

Adding a regional variant later is additive: drop a new `<locale>.json` next
to the base catalogs and it participates in the fallback chain automatically.

## 2. Decisions (ADR-lite)

### D1 — Catalog format: **JSON** for the CLI foundation

**Decision:** message catalogs are flat JSON keyed by dotted translation IDs.
A value is either a string or a plural-forms object.

**Why:** zero new dependencies for the day-one foundation, trivially
diffable, and the same format the frontend JS can consume. gettext/PO has
richer tooling (pybabel) but is JS-hostile and heavier than the foundation
needs.

**Consequence / later:** the *string-extraction* workstreams (PUP-480 public,
PUP-481 private, PUP-477 frontend) may layer Babel/pybabel on top for
extraction + compilation without changing this runtime contract — Babel can
emit JSON. The Python frontend (PUP-478) will use `jinja2.ext.i18n`; whether
its catalogs are PO or JSON is that story's call, but the CLI stays JSON.

### D2 — Missing keys **never raise**

A key absent from every catalog in the fallback chain renders as the **key
itself** (`nope.not.here`). This guarantees the app never crashes on a
translation gap, and an untranslated string is visually obvious on screen.

### D3 — Fallback chain, most-specific-first, default last

`zh-Hans-CN` → `zh-Hans` → `zh` → `en-US`. The default (`en-US`) is always
appended, so a key present only in the source catalog still resolves in any
locale.

### D4 — Interpolation is `{param}`-style and forgiving

We use `str.format_map` with a safe mapping. A missing `{param}` leaves the
placeholder intact instead of raising. Placeholders are **never** part of the
translatable text semantics — translators reorder them freely.

### D5 — Backend localization model: **code + params, localize in the CLI**

For `puppy-backend` (PUP-479): the backend returns **stable machine error
codes + params** (e.g. the `QuotaExceeded` struct), and the CLI localizes at
the edge. The backend does **not** bake N languages into the Rust binary.

Rationale: the struct-first design already separates data from prose, and
CLI-side localization avoids adding an `Accept-Language`/`x-puppy-locale`
round-trip for the common path. The only mandatory backend prose is the
`fake_llm_response` policy blurbs (which are returned as assistant turns and
printed verbatim) — those get a small dedicated catalog. **Before** any of
this, consolidate the duplicated `rate_limit_error` builder
(`openai_responses.rs` vs `llm_shim.rs`) so we don't translate one and orphan
its twin.

### D6 — Model-facing system prompts are **out of scope** for UI i18n

Translating agent/model system prompts changes LLM behavior and is a separate
track, not part of UI localization. Do not run them through the string
extractor.

### D7 — The `walmart_specific` plugin corpus is its **own epic** (PUP-482)

External translators cannot access the private plugin, so its ~727 strings
live behind a different security/translation boundary and are decoupled from
the public catalogs.

## 3. How the runtime resolves a locale

Precedence, highest first (see `code_puppy/i18n/locale.py`):

1. `CODE_PUPPY_LOCALE` env var (explicit override)
2. POSIX vars: `LC_ALL` → `LC_MESSAGES` → `LANG` → `LANGUAGE`
3. The persisted `locale` config key (`puppy.cfg`) — set via `/set locale`
4. Default: `en-US`

At boot, resolve once:

```python
from code_puppy.i18n import use_detected_locale
from code_puppy.config import get_value

use_detected_locale(get_value("locale"))
```

## 4. Call-site usage

```python
from code_puppy.i18n import t, ngettext, lazy

emit_info(t("startup.welcome", name=owner))          # simple
emit_info(ngettext("files.deleted", count=n))        # plural-aware
emit_info(lazy("startup.ready"))                      # resolved at render
```

`lazy(...)` returns a deferred translation resolved when the message bus calls
`str()` on it — use it for strings produced before the locale is finalized.
The single emit choke point (`messaging/message_queue.py::emit_message`)
resolves `LazyTranslation` automatically; plain strings pass through untouched.

Locale-aware formatting:

```python
from code_puppy.i18n import format_number, format_datetime
format_number(1234567)                # "1,234,567" (en) / "1.234.567" (de)
format_datetime(dt)                   # ISO for now; Babel-backed later
```

### Optional plugin catalogs

Plugins do not need to provide translations. A plugin that never calls the
registration API loads exactly as it did before. Plugins that opt in register
one locale-resource directory at module scope in their existing
`register_callbacks.py`; there is no additional entry point or callback phase.

For an installed package, pass an `importlib.resources` Traversable. Do not use
`as_file()` or save a temporary extraction path — Code Puppy streams and
validates the resources during plugin loading, then keeps the catalogs in
memory:

```python
# acme_weather/register_callbacks.py
from importlib.resources import files

from code_puppy.i18n import register_plugin_catalog

register_plugin_catalog(files("acme_weather").joinpath("locales"))
```

The plugin's existing entry point remains the only discovery declaration:

```toml
[project.entry-points."code_puppy.plugins"]
acme_weather = "acme_weather.register_callbacks"

# Hatch example for an src-layout wheel. Verify the built wheel contains the
# JSON files; package-data omissions are diagnosed at plugin load time.
[tool.hatch.build.targets.wheel]
packages = ["src/acme_weather"]

[tool.hatch.build.targets.wheel.force-include]
"src/acme_weather/locales" = "acme_weather/locales"
```

Loose user and trusted project plugins can use the same API with a filesystem
adapter:

```python
from pathlib import Path

from code_puppy.i18n import register_plugin_catalog

register_plugin_catalog(Path(__file__).parent / "locales")
```

Project catalogs become visible when a trusted project plugin hot-loads. Catalog
registration is transactional across the complete import: nested plugin loads
act as savepoints and only the successful outermost load publishes their
providers. A failed plugin import discards its staged catalog. Registration
must finish synchronously during loading; an asyncio task that inherited loader
context but runs after that transaction closes is rejected rather than treated
as the plugin owner. `/plugins disable` and `/plugins enable` invalidate the
locale snapshots, so translations disappear and return with the plugin's
runtime state without duplicate registration. The Python module itself is not
unloaded when a plugin is disabled.

#### Catalog contract

The loader-derived plugin name owns a canonical key prefix. Runs of `.`, `_`,
and `-` normalize to `-` and ASCII letters normalize to lowercase. For the
entry-point name `acme_weather`, every key must therefore start with
`plugin.acme-weather.`:

`acme_weather/locales/en-US.json` (required source catalog):

```json
{
  "plugin.acme-weather.forecast": "Forecast for {city}"
}
```

`acme_weather/locales/es.json` (optional and partial):

```json
{
  "plugin.acme-weather.forecast": "Pronóstico para {city}"
}
```

`en-US.json` is required when a plugin opts in. Locale filenames must use the
canonical form returned by `normalize_locale` (`pt-BR.json`, `zh-Hans.json`,
not case/underscore variants). Every key in another locale must exist in that
source catalog; omitted translations fall through the normal locale chain to
`en-US`. A translated entry must retain the source entry's string-versus-plural
shape and the exact placeholders recognized by the runtime (`{name}`-style bare
identifiers). Plural objects may use only the categories Code Puppy supports:
`zero`, `one`, `two`, `few`, `many`, and `other`; `other` remains required.
Files and JSON keys are processed deterministically. Repeating an identical
registration is harmless, while a second, different provider for the same
owner or canonical namespace is rejected.

Each provider is validated before any of it is published. Invalid JSON,
duplicate keys, a non-object root, invalid string/plural values, unsafe locale
filenames, out-of-namespace keys, missing source keys, and missing package data
all reject that provider atomically. Ordinary malformed/provider and
filesystem/archive resource errors are diagnosed the same way and return
`False`, so optional i18n data does not crash the host. `MemoryError` and
process-control `BaseException` subclasses such as `KeyboardInterrupt` and
`SystemExit` deliberately propagate; they are not malformed optional input and
must not be converted into a warning. Rejections name the plugin and resource.

#### Tier identity and deterministic discovery

Installed entry points load first in sorted name order. An installed plugin
suppresses a same-named legacy bundled copy and same-named user plugin. A
trusted project plugin suppresses a same-named user plugin during the existing
pre-scan, then loads after installed/bundled plugins; a same-named builtin is
still loaded and produces the existing shadow warning. Catalog identity is
loader-derived and process-wide: if two loaded tiers use the exact same owner,
the first identical registration is idempotent but a different later provider
is rejected. Names such as `sample_plugin` and `sample-plugin` are distinct
plugin identities but share one canonical catalog namespace; sorted user and
project discovery makes the first provider deterministic and diagnoses the
later collision rather than silently overriding it.

The namespace rule prevents accidental catalog collisions; it is not a
security boundary. This API deliberately cannot replace core keys. Existing
`add_catalog_dir(path)` behavior is unchanged and remains the compatibility
path for language packs or intentional core overrides: later directories win.
A loose filesystem plugin supporting older Code Puppy versions may
feature-detect `register_plugin_catalog` and fall back to `add_catalog_dir`:

```python
from pathlib import Path

import code_puppy.i18n as i18n

locales = Path(__file__).parent / "locales"
register = getattr(i18n, "register_plugin_catalog", None)
if register is not None:
    register(locales)
else:
    i18n.add_catalog_dir(str(locales))
```

An installed-resource plugin should instead declare a minimum Code Puppy
version once the first release containing `register_plugin_catalog` is
published; there is no safe persistent-path fallback for a zipped resource.
Do not retain an `as_file()` temporary path.

Adding a new locale JSON file adds **messages only**. Plural selection and
number/date formatting keep their existing fallback tables. A language absent
from those tables still uses the existing English plural and formatting
fallbacks until core gains explicit rules.

### Measuring extraction progress

Migrating ~2,000 `emit_*` / `console.print` sites is easy to get wrong by
hand, so `code_puppy/i18n/audit.py` statically classifies every user-facing
emit call site as **extracted** (already a `t()`/`ngettext()`/`lazy()` call),
**raw** (a hard-coded literal still needing extraction), or **dynamic** (the
text comes from a variable — nothing to extract here).

```bash
python -m code_puppy.i18n.audit                 # summary + coverage %
python -m code_puppy.i18n.audit --top 15        # worst files to attack first
python -m code_puppy.i18n.audit --list          # every raw site (file:line)
python -m code_puppy.i18n.audit --json          # machine-readable
python -m code_puppy.i18n.audit --fail-under 25 # CI gate (exit 1 if under)
```

Use `--top` to pick the next high-value module to extract, then re-run to
watch coverage climb. Pair it with the runtime pseudolocalization test
(`tests/i18n/test_i18n_audit.py`) which *proves* a migrated module leaks no
un-externalized strings.

## 5. Translator quickstart

To add or update a translation:

1. Open the base catalog `code_puppy/i18n/locales/en-US.json` to see the keys
   and English source strings.
2. Create/edit `code_puppy/i18n/locales/<your-locale>.json`. Include only the
   keys you're translating; anything you omit falls back automatically.
3. Keep `{placeholders}` **exactly as written** — reorder them for grammar,
   but don't rename or remove them.
4. For plurals, provide the categories your language uses. Only `other` is
   required; add `one`/`few`/`many`/etc. as needed:
   ```json
   "files.deleted": { "one": "…", "other": "…" }
   ```
   Supported plural rules live in `code_puppy/i18n/plurals.py`. If your
   language isn't listed there yet, it defaults to the English one/other rule
   — file a note so we can add the correct CLDR rule.
5. Keep top-level catalog keys alphabetized. Nested plural objects retain their
   canonical CLDR category order rather than alphabetical order.
6. Run the tests: `pytest tests/i18n/`.

### Pseudolocalization (catching missing translations)

Set the locale to `en-XA` to render every string in an accented, padded,
bracketed form: `⟦Ŵéĺçöḿé ţö Çöđé Þüþþý⟧`. Any text that shows up **without**
brackets is a hardcoded string that skipped the catalog — a bug. This is what
the pseudolocale CI check (PUP-476) will assert on.

## 6. Where things live

```
code_puppy/i18n/
├── __init__.py      # public API: t, ngettext, lazy, format_*, set_locale…
├── locale.py        # detection, normalization, fallback chain
├── catalog.py       # JSON loader, merge, missing-key lookup
├── translate.py     # Translator singleton, t(), ngettext(), LazyTranslation
├── plurals.py       # CLDR-lite plural category selection
├── formats.py       # locale-aware number/date formatting (stdlib for now)
├── pseudo.py        # pseudolocalization transform
└── locales/
    ├── en-US.json   # source / default
    ├── es.json      # Spanish base (Latin American es-419 folded in)
    └── fr-CA.json   # Canadian French
```
